# 04 技术架构

> 本文描述目标架构。当前配置与受限 Agent/阶段团队执行子集、尚未验证的部署边界见 [实施状态](./10-implementation-status.md) 和 [运行契约](./14-agent-runtime.md)。

## 1. 已选技术栈

| UI       | Element Plus、自定义主题、Vue Router、Pinia | 基础控件、路由和页面状态；不是直接套传统 CRUD 后台 |

| 后台任务 | BullMQ、Redis                               | 队列、并发控制、延迟执行与调度触发                 |
| 通信     | REST、SSE                                   | 操作提交与状态查询；实时单向进度                   |
| 文件     | 持久化目录，预留 S3 兼容存储接口            | 图片、附件、导出包；首版不强制对象存储服务         |
| 入口     | Caddy                                       | 静态 Web、反向代理、满足域名与验证条件时配置 HTTPS |

| 工程     | pnpm workspace、ESLint、Prettier            | 建议的依赖与代码质量基线                           |
| 测试     | Vitest、Jest、Playwright                    | 前端单测、后端与集成测试、端到端测试               |

工程已使用精确依赖和锁文件，并提供固定镜像标签；本地构建已验证，镜像拉取、Linux 兼容性和安全维护状态仍待验证。详见实施状态。不要使用浮动 `latest` 作为正式部署方案。

## 2. 设计原则

- 模块化单体：模块按业务划分，不为每个功能建立微服务。
- API 与 Worker 分进程：共同代码、共同镜像，不让长任务依赖网页连接。
- PostgreSQL 是业务事实来源；Redis 是执行调度基础设施，不是唯一内容存储。
- 专家和 Skills 是业务能力，不先绑定某个通用 Agent 框架。
- 先使用外部模型 API，不要求 GPU、自建推理或 Python 服务。
- 文件、模型、发布采用小而清晰的适配接口；按 D-011 实现创作能力包的分享/发现，不扩展为与创作无关的通用插件平台或第三方私有市场镜像。

## 3. 运行拓扑

```text
Browser
   |
 HTTPS
   |
Caddy -- static web files
   |
 /api + SSE
   |
 API ------------------------ PostgreSQL
   |                               |
   | durable run + outbox          | runs / steps / outputs
   |                               |
   +-------- Redis / BullMQ ---- Worker
                                  |
                            Model providers
                            Controlled tools
                            Platform adapters (later)

API + Worker -> shared persistent assets directory
```

建议五个常驻容器：`gateway`、`api`、`worker`、`database`、`redis`。前端构建产物进入 gateway 镜像，不另运行 Vite 开发服务器。

第一版允许 API 与 Worker 共享同一主机上的持久化素材目录。未来跨主机部署 Worker 前，必须迁移到共享对象存储或明确的文件访问服务，不能假设本地目录自动共享。

当前没有素材目录；包资源、Agent 结果与调用账本保存于 PostgreSQL。Worker 可通过 model_egress 发起白名单 HTTPS 模型请求，仅开放两个包内只读工具。API 同样接入 model_egress 执行用户显式确认的基础连接检查，检查独立持久化；数据库/Redis 仍只在内部网络，API 不发布主机端口。素材与发布适配器尚未实现。model_egress 不是网络层白名单，应用仍检查 URL/DNS/socket。

## 4. 业务模块

| 模块           | 职责                                                               |
| -------------- | ------------------------------------------------------------------ |
| auth           | 管理员初始化、登录、会话和归属校验                                 |
| accounts       | 平台账号档案、作者人设、默认创作配置                               |
| experts        | 单专家/专家团定义、版本、默认能力、能力包和试运行                  |
| skills         | SKILL.md/资源、版本、发现/按需加载和受控工具边界                   |
| agents / teams | 目标执行模块：独立上下文、成员调用、任务依赖、消息、预算与结果汇总 |
| materials      | 素材、来源、归属、分类与搜索                                       |
| assets         | 文件元数据、上传、授权读取、导出产物                               |
| models         | 供应商适配、凭证引用、能力、用量与费用估算                         |
| workflows      | 少量代码定义的步骤模板、校验和检查点                               |
| creation       | 任务创建、配置快照、步骤推进、候选内容                             |
| contents       | 内容版本、编辑、审核、导出                                         |
| schedules      | 时间规则、时区、选题消费、启停与漏跑策略                           |
| tasks          | 运行状态、Outbox、队列、取消、重试与核对                           |
| publishing     | 平台能力与发布记录；第一版只保留边界和导出入口                     |
| settings       | 非敏感设置、通知和运行配置                                         |

模块通过服务接口交互，避免跨模块直接修改对方表数据。队列载荷只包含任务标识等最小信息，不复制完整素材或密钥。

当前账号、专家、技能和包管理集中实现于 `modules/catalog`，团队定义嵌入专家版本；上表是职责边界，不表示已有所有目录或服务。`modules/models` 与 `modules/tasks` 已实现 C2/C3 的受限 Agent/阶段团队执行子集，动态派发、追问与交互继续仍待完成。成员独立调用，不能通过一次模型调用模拟多成员替代，也不必为每位专家建立独立微服务。

## 5. 后台任务可靠性

创建任务时，在一个数据库事务里保存任务记录与待投递事件（Outbox）。Dispatcher 将事件投递到 BullMQ；定期对账确保 API 在事务提交后崩溃不会永久丢任务。

队列采用至少一次处理的假设，执行器必须支持：

- 业务运行唯一键、步骤领取锁或租约，避免多 Worker 同时执行同一步。
- 已完成步骤结果落库，重启后从明确检查点恢复。
- 有上限的退避重试、超时、取消与失败分类。
- 结果未知时人工核对或调用供应商查询接口，不盲目重复有副作用的请求。
- 人工确认保存为数据库状态并释放 Worker，确认后重新调度。

不承诺端到端 exactly-once。数据库去重和队列去重不能替代外部模型或发布接口自身的幂等与结果查询。

当前模型路径先持久化 ModelInvocation/预算，再发请求；团队独立成员复用同一账本机制。确认成功且摘要一致的响应可恢复，in_flight/unknown 进入 needs_review 而不重发。取消尽力中断，不保证外部未执行/免收费；核对只追加说明并关闭。详情见 14，不承诺 exactly-once。

定时计划以数据库配置为准。触发时先创建具有唯一 `(schedule_id, scheduled_for)` 的执行记录，再通过相同 Outbox 链路入队。默认跳过停机期间过期时点，避免恢复时集中调用模型。

## 6. 模型适配

统一接口覆盖请求校验、流式输出、结构化结果、取消、超时、用量与错误分类。供应商特有参数只在适配器内处理，不把某一家 SDK 对象传入所有业务模块。

能力按供应商和模型分别登记：文字、图片、音频、视频、结构化输出、工具调用等。不假设所有“兼容 API”具有完全相同的功能。

第一版先验证文字生成与专家调用闭环。平台 SDK 版本和真实模型清单在 M0 阶段确认。没有价格信息时显示估算不可用，不显示零成本。

## 7. 内容与编辑

结构化编辑器 JSON 是正文主数据，包含 schema 版本；标题、封面、附件和导出参数一起进入内容版本。HTML、Markdown 和平台格式是派生输出。

生成结果先写候选内容，用户确认后采用。前端通过版本号或 ETag 提交修改，后端检测冲突，避免后台生成覆盖前台编辑。

公众号排版不由 Tiptap 自动保证。导出适配层负责样式转换、HTML 清理、图片处理及真实平台验证。

## 8. 实时进度

REST 负责提交任务、确认、取消和获取当前状态；SSE 负责实时通知，不作为唯一状态来源。断线后先查询数据库中的最新任务快照，再按事件游标补齐可保留的事件。

0.0.1 实现数据库快照型 SSE：新连接发送最新状态、终态断开；已有取消与未知核对，无持久化事件回放、Token 流或确认继续接口。具体事件见实施状态。

流式 Token 可以是临时显示，不能要求每个 Token 都永久保存。最终正文、步骤结果和业务状态必须持久化。网关需允许长连接并关闭影响流式反馈的缓冲。

## 9. 代码结构

以下目录已经创建；业务能力逐步扩展，不为尚未支持的功能创建空页面：

```text
apps/
  web/
  server/
    src/
      main-api.ts
      main-worker.ts
      modules/
      common/
      config/
packages/
  contracts/
infra/
  docker/
docs/
```

`contracts` 存放允许前后端共享的接口和 schema，不暴露数据库实体或凭证字段。API 和 Worker 共用 `apps/server`，通过不同入口启动。

## 10. 暂不采用

不默认采用 Kubernetes、Kafka、微服务、独立向量库、复杂 Agent 框架、实时协作编辑、通用拖拽工作流和本地浏览器发布服务。有真实需求时通过决策记录引入。

参考文档：[BullMQ](https://docs.bullmq.io/)、[Tiptap 编辑器](https://tiptap.dev/docs/editor/getting-started/overview)。具体 API 使用需以实施时锁定版本的文档与测试为准。
