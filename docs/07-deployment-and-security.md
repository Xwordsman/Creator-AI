# 07 部署与安全

## 1. 部署目标

Docker Compose 单服务器部署，浏览器通过统一域名访问。不要求用户安装桌面客户端，不默认需要 GPU。CPU、内存与磁盘最低要求在文字创作负载测试后公布，不在未测试前承诺低配服务器能够稳定运行所有功能。

本文是部署设计和验收要求。0.1.0 已提供独立生产 Compose、配置检查、安装/升级/备份工具与源码交付包，具体命令见 [服务器安装](./21-production-release.md)。尚未在真实 Docker 环境完成启动、持久化和恢复验收；按服务器安装版交付与完成生产环境验收是两件事，实际验证记录见 [实施状态](./10-implementation-status.md)。

## 2. 容器职责

| 服务     | 职责                                   | 对外访问                    |
| -------- | -------------------------------------- | --------------------------- |
| gateway  | Caddy、前端静态文件、反向代理、HTTPS   | HTTP/HTTPS 入口             |
| api      | 登录、业务 API、SSE、文件授权访问      | 只在内部网络由 gateway 访问 |
| worker   | 队列执行、专家步骤、计划触发和任务对账 | 不开放公网业务端口          |
| database | PostgreSQL 业务数据                    | 仅内部网络                  |
| redis    | BullMQ、必要的运行协调                 | 仅内部网络                  |

API 与 Worker 共用镜像，通过不同启动命令区分。应用镜像按最小权限运行，不以 root 运行业务进程，不挂载 Docker socket，不使用特权容器。

当前仅 gateway 发布端口；数据库/Redis 只在内部网络，API 与 Worker 另接 model_egress，分别用于用户显式连接检查与创作执行。该网络只提供连通，不是防火墙白名单；应用强制 HTTPS 精确主机、全部 DNS 地址检查和实际 socket 绑定，不跟随重定向。严格环境还需出口代理/防火墙。`compose.dev.yaml` 只将数据库/Redis 绑定主机 127.0.0.1；Docker 冒烟覆盖 API/Worker 为仅内部网络并强制 mock。

本地开发可使用非生产入口，但公网部署需要正确 TLS 配置。自动证书依赖域名解析、外部连通与证书验证条件，不能仅因为使用 Caddy 就声称 HTTPS 自动可用。

## 3. 数据持久化

必须持久化并明确位置的数据：

- PostgreSQL 数据及可恢复备份：账号、专家/团队、技能及版本/包资源、内容、计划和任务。
- 素材目录：图片、附件、导出产物和内容哈希。
- Redis 数据：开启并验证与 BullMQ 兼容的持久化与淘汰设置，队列实例不采用会随意淘汰队列键的策略。
- Caddy 需要保留的证书与运行状态。
- 独立保管的主密钥和部署配置；不要把它们混入普通公开备份。

容器重建不能丢稿件。Redis 持久化是补充，不替代数据库里的业务任务记录、Outbox 与重建对账能力。

首版素材目录由 API 和 Worker 按实际权限共享。文件名和对象键由服务端生成；不得把用户传入路径直接拼进文件系统操作。

0.0.1 没有账号素材上传或发布凭证；模型 Key 已加密存库，主密钥由环境单独注入/备份。能力 ZIP 以文本/base64 存 PostgreSQL JSONB，不解包到磁盘；备份还需包括模型连接、调用/工具/成员证据与核对说明。卷仍仅 PostgreSQL、Redis、Caddy；没有素材卷。

## 4. 初始化与认证

- 首个管理员初始化必须有一次性引导凭证、受限入口或等效保护，避免公网部署时被陌生人抢先注册。
- 初始化完成后关闭引导入口，拒绝默认公开密码。
- 密码使用成熟的密码哈希方案，不做可逆加密或自定义哈希。
- 登录限流，支持会话注销、过期与撤销。
- 同源会话遵循 Cookie、CSRF 和 Origin 校验规则，参见 API 文档。
- 归属校验覆盖普通接口、SSE、导出下载、图片读取和后台任务，而不是仅校验页面登录。

当前首次管理员使用本地交互 CLI 和数据库锁初始化；已有用户后关闭引导。没有默认口令、公开注册接口或浏览器引导码。密码重置与变更尚未实现，不能把 CLI 重复初始化当作账号恢复方式。

## 5. API 密钥与平台凭证

- 密钥只在后端使用；保存后前端只接收遮罩和必要状态。
- 数据库采用经过验证的认证加密方案，记录密钥版本与用途；加解密主密钥不与数据库明文存放在一起。
- 主密钥通过受控文件或部署秘密注入；Compose 的文件挂载本身不等于密钥管理服务或磁盘加密。
- 不在日志、错误、URL、SSE、队列载荷、导出包和 Git 中记录真实密钥。
- 支持停用与后续轮换；恢复备份时需具备对应旧密钥版本，否则凭证不可用。
- 权限以执行时有效状态为准；停用模型连接或平台授权后，排队任务不能继续用旧快照越过限制。

当前实现认证加密，随机 IV、AAD 绑定 owner 与连接 ID；同一 64 hex 主密钥必须稳定提供给 API/Worker。没有主密钥版本迁移/轮换入口，不能直接换密钥后继续读原密文。连接可启停且每次发送前重新检查，已有在途请求不能撤回。启用步骤见 14。

平台 Cookie 或 Token 即便由用户提供，也需要按高敏感凭证处理。第一版不要求用户为了写文章就上传平台登录信息。

## 6. 文件与内容安全

- 上传校验实际类型、扩展名、大小、数量和内容解析限制，不仅相信客户端 MIME。
- 不在公开静态根目录直接暴露全部素材；读取必须校验归属或使用受限短期访问机制。
- HTML 预览、导出和复制链路做白名单清理；模型输出与用户上传内容都属于不可信输入。
- 能力包导入与导出都校验路径、条目与容量，防止路径穿越、链接、规范化重名、解压炸弹和越权资源访问。
- 记录素材来源与使用权说明，不能把抓取到的图片自动视为可商用。
- 前端预览布局不能替代真实目标平台的排版兼容性测试。

### 已实现的能力包边界

- ZIP 请求最大 2 MiB，最多 128 条目、单文件 512 KiB、累计解压 4 MiB；不自动递归解开嵌套归档。普通 JSON 请求 64 KiB，专家/技能配置路由 2 MiB，另有字段级限制。
- 仅内存解析、归属校验后存库，不写用户提供的服务器路径。拒绝绝对路径、反斜杠、路径穿越、链接、加密与重名；YAML 不允许别名及重复键。
- `scripts/`、二进制与未知工具声明仅作为资源存档。没有脚本执行器、依赖安装、MCP/桌面授权或已实现的沙箱，不因导入成功而获得这些能力。
- 资源查看以受控文本方式展示，不执行 HTML/Markdown 脚本；导出需要 owner 会话。导入事务遇到同 key 冲突整体回滚。
- 包来源与许可证仍需用户核对；未知字段和私有工具依赖不能宣称等价支持。原始包下载是存档文件重打包，不是原 ZIP 字节还原。
- 总库容量、版本保留、导入频率及完整第三方依赖分析尚未完成。当前不能当作面向不可信多租户的公网包托管服务。

后续受控脚本工具须独立实现资源/网络隔离，不挂应用凭证、宿主目录或 Docker Socket。Docker 部署本身不构成任意代码沙箱；服务器不能默认控制浏览器所在电脑的桌面。

## 7. 出站请求与工具权限

第一版来源链接只是元数据，不主动实现任意 URL 抓取。未来增加网页采集、Webhook、远程图片或自定义模型地址时，需要 SSRF 防护：

- 校验协议、目标主机、解析结果和重定向链。
- 默认拒绝访问云元数据、环回、内网和链路本地地址；确需内网模型时，由管理员显式配置严格白名单。
- 设定连接/读取超时、响应大小限制和重定向上限。
- 出站白名单与鉴权配置分开，避免凭证被发送到任意重定向目标。
- 权限由确定性后端逻辑执行，不能交给提示词或模型自行判断。

## 8. 调度、恢复与资源上限

- 计划保存 IANA 时区；界面显示下一次实际执行时间。
- 默认停机漏跑不补跑；暂停与恢复不一次性执行所有历史计划。
- API 与 Worker 都需要健康检查，启动顺序使用依赖就绪判断而不是固定睡眠。
- 区分进程存活、依赖可用和任务可处理；模型供应商暂时故障不应触发无限重启循环。
- Worker 支持优雅退出；有限等待当前任务，再通过检查点与结果核对恢复。
- Redis、数据库或磁盘不可用时明确报错与降级，不把未保存结果标记为成功。
- 设置每账号/模型并发、单任务时长、输出长度、重试次数、上传大小和保留策略。
- 预算包括并发预留和已知费用；供应商账单可能延迟，模型用量也可能缺失，不能承诺本地估算是绝对硬上限。

## 9. 备份与恢复

备份范围至少包括数据库、素材和配置；解密主密钥独立安全备份。仅复制正在运行的 PostgreSQL 数据目录不是通用可靠备份方案。

建议首版采用短维护窗口的可验证流程：

1. 暂停新计划与写入，停止领取新任务，等待或核对在途操作。
2. 使用数据库支持的一致性备份方式保存业务数据。
3. 在写入仍暂停时备份对应素材与部署元信息，记录应用版本、迁移版本和文件清单。
4. 单独确认所需解密密钥可恢复，再恢复正常运行。
5. 在隔离环境恢复数据库和素材，校验内容、专家版本、文件引用与凭证可解密性。
6. 恢复后的 Worker 默认不开启外部副作用；先核对任务与发布状态，再由管理员恢复调度。

Redis 可重建不等于可以立即重放所有任务。已经发给供应商或平台但结果未知的操作必须先核对。备份保留周期、容量上限和删除策略在部署配置中明确。

2026-11-02 本机预览先后进行能力目录和 Agent 运行时升级，均在停止 API/Worker/数据库/Redis 并确认 PostgreSQL 已退出后完成数据目录冷备份，再应用增量迁移。显式原有业务列哈希一致；新增配置示例或模拟任务均在核验后才写入。**这只证明这两次升级保留原数据，不代表冷备份已恢复验证，也不代替 Docker 卷/服务器恢复验收。** 路径与验证记录见 10。

## 10. 升级与回退

- 发布说明标注数据库迁移、配置变化和已知不兼容项。
- 升级前备份，迁移执行一次，验证健康和关键流程后再恢复计划。
- 不假设旧镜像能读取升级后的数据库；回退必须验证兼容性或恢复匹配备份。
- 对失败迁移和恢复过程保留诊断信息，不提供默认删除数据卷的“修复命令”。

## 11. 运维验收

必须演练容器重建、机器重启、数据库暂时不可用、Redis 恢复、模型限流、磁盘不足、备份恢复和 SSE 重连。后续引入发布时还需演练“提交成功但响应丢失”，确保不会重复发布。

已提供 `pnpm test:docker` 隔离冒烟入口，覆盖当前 mock 切片的真实镜像启动、Caddy/SSE 和保留卷重建场景，详见 [Docker 隔离验收](./11-docker-smoke-acceptance.md)。脚本不复用正式 `.env` 或数据卷；它尚未在本机 Docker 上执行，且不替代完整备份恢复和故障演练。
