Creator-AI 是面向个人创作者的开源 AI 自媒体创作工作台，使用浏览器访问，通过 Docker 部署在用户自己的服务器上。它围绕账号、专家、Skills、素材和创作计划组织工作，而不是要求用户每次重新开启对话、重复介绍人设。

## 如何阅读

1. 先读产品范围和功能需求，确认要解决什么问题、第一版不做什么。
2. 实现专家或创作功能前，阅读专家设计、领域状态和 13 号能力对齐计划；12 号核对是扩展前的历史证据。
3. 编码前对照技术架构及 API 约定，部署前对照安全文档。
4. 每个阶段按开发路线中的验收场景交付，而不是只检查页面是否存在。

## 当前确定的方向

- 产品形态：自部署 Web 工作台，Docker Compose 部署，个人使用优先。
- 核心体验：选择账号和专家，复用 Skills 与素材，手动或定时创作。
- 专家中心是第一版一级模块，不可简化成一段账号人设或普通聊天入口。
- 按 D-011 完整对齐 WorkBuddy 专家、Skills 与 AI 专家团的功能语义；独立实现，不复制私有代码/内容。技能库是独立模块，真实成员协作是必做能力。
- 第一版重点：公众号图文、编辑审核、可靠导出；可使用通用流程生成口播文本，不制作完整视频。
- 自动化边界：自动创作到待审区；平台草稿与受控发布属于后续独立接入能力。
- 技术栈：Vue 3、TypeScript、Vite、Element Plus、Tiptap、NestJS、PostgreSQL、TypeORM、BullMQ、Redis、Caddy。
- 架构：模块化单体，API 与 Worker 独立进程，共用后端代码及镜像。

## 文档状态约定

- **已确认**：来自已完成的产品讨论或明确认可的技术选型。
- **建议基线**：为落地提出的字段、接口、状态和安全约定；开发应先按此保持一致，必要时通过决策记录修订。
- **待验证**：涉及第三方权限、兼容性、许可、成本等，不得作为已支持能力宣传。
- **已实现**：只有代码完成并通过相关验收后，才可以在版本记录中标记。

本套文档不会把设计提议等同于实现结果。01-09 仍以目标规格为主，当前实际迁移、可调用 API 和验收缺口以 [实施状态](./10-implementation-status.md) 为准；启动步骤见 [仓库 README](../README.md)。13 区分完整目标与已交付子集，不能因为配置页存在就声称真实专家/Skill/团队运行或第三方兼容已经完成。

## 文档维护规则

- 范围变化同时更新产品范围、功能需求、路线与决策记录。
- 专家规则、内容版本或任务语义变化，同时更新领域状态和验收场景。
- 平台能力只有完成权限核验与实际测试后才可标记为可用。
- 不在文档、示例或仓库中记录真实 API 密钥、平台 Cookie、Token 和用户私有素材。
- 新增依赖需要检查许可证；基础能力不默认依赖付费插件或外部托管服务。
- 具体运行时、依赖和镜像版本在初始化工程时验证兼容性并锁定，不在本基线中猜测版本号。
