# 16 动态专家团与持久化交互

> 0.0.1 开发预览，独立实现。此契约不代表 WorkBuddy 全量对齐、真实模型内容质量或 Docker 验收。

## 1. 两种运行模式

- `team-v1`：沿用原结构化阶段、同阶段最多三成员并行、负责人独立汇总。旧快照和历史任务不升级、不重写。
- `team-dynamic-v1`：创建团队任务时显式提交 `teamMode: "dynamic"`。负责人通过独立模型调用提出计划、补问、确认或汇总；成员进行真实独立调用。
- 动态模式仍必须选择已配置模型，不回退为模板或一次调用扮演多人。单专家不能提交团队模式。成功稿的修改分支继承原模式和冻结配置，建立新预算和新账本。
- 动态模式当前逐任务串行调度。等待用户前没有其他成员 HTTP 请求在途；不是并行自主 Agent 网络。固定阶段模式的并行能力不变。

## 2. 实际流程

1. 负责人规划调用只接受有界严格 JSON，不能运行任意指令或添加新成员。
2. `delegate` 提案列出已有非负责人成员、具体任务和已交付任务 UUID 依赖。每次提案先持久化并等待用户确认；同意后才在事务中建立成员任务，拒绝后按反馈重新规划。
3. 成员可以 `deliver` 交付，`request_peer` 请求另一位已有成员补充，或 `ask_user` 询问用户。不能向自己或负责人提出同伴请求。
4. 同伴补充真实执行一次成员调用，只允许 `deliver`，不能无限转发。原成员随后以新任务接收补充结果；原提问、同伴答复与继续任务均保留。继续任务仍可在总次数限制内再次追问。
5. 成员向用户补问后，用独立新任务接收答复并继续工作；不改写原问题任务或复用原调用号发送新上下文。
6. 所有本批任务完成后，负责人再次规划，可继续派工审校、追问用户、请求取舍确认或选择 `finalize`。
7. 至少有一份真实成员交付才允许 `finalize`；随后另建负责人汇总任务，输出完整纯文本候选正文，而非直接把规划 JSON 当成成稿。

结构化阶段在动态模式中只是负责人参考，不是调度指令。模型协议错误、越权成员、未来依赖、重复成员、错误动作或超限直接停止并保留原始响应，不自动付费纠错重试。系统不能保证模型理解或遵守所有创作建议，用户仍需审核内容。

## 3. 持久化与 HTTP

新增 `team_actions`，每个源 AgentRun 最多一个结构化动作，记录指令、`waiting/applied/peer_wait`、答复及派生任务 UUID。动作与派生任务在同一数据库事务内写入；唯一约束防止重复应用。模型原始结果仍在 `agent_runs`，调用在 `model_invocations`，不使用浏览器内存作为运行事实。

`GET /api/v1/creation-runs/:id` 和 SSE 的 `execution.collaboration` 返回当前动作及历史。消息类型增加计划、问题、答复和确认。`planner` 是负责人规划角色，`lead` 是独立汇总角色。

用户响应：

```http
POST /api/v1/creation-runs/:id/actions/:actionId/respond
Content-Type: application/json
X-CSRF-Token: <session csrf>

{"answer":"同意按这个分工执行","approved":true}
```

- 需要会话、精确 Origin、CSRF 和任务 owner。动作不存在或不属于任务返回 404；字段、路径 UUID、2–2000 字答复由共享契约验证。
- `delegate/confirm` 必须显式提供布尔 `approved`；拒绝是 `false`，不是取消任务。`ask_user` 只提交 `answer`，不得夹带批准字段。
- 动作 UUID 是一次性决策标识，不另要求 Idempotency-Key。相同已答动作和相同规范化内容返回当前任务；并发只写一条答复。不同内容再次提交返回 409，不能改写历史决定。
- 只接受 `waiting_user` 的待答动作。写入答复、转 `queued`、清空 Outbox 投递时间在同一事务，随后由现有 Dispatcher 重新入队。
- 已答动作重试不会重置已运行任务、重复派工、续开取消任务或新建收费任务。未知网络响应可重试同一内容；不要为消除超时而生成新动作。

## 4. 等待、恢复与预算

状态新增 `waiting_user`，不是终态，也不是失败或 `needs_review`。状态路径为 `running -> waiting_user -> queued -> running`；等待时释放租约，Worker 返回，不阻塞工作线程，Dispatcher 不投递等待任务。旧队列消息到达等待任务也不能领取。

等待时可以刷新、关闭页面和重启服务。答复与任务关系以数据库为准；前端仅按当前用户/任务/动作在本标签页 sessionStorage 暂存未确认提交的文本与批准选择，不跨设备共享，不自动重试。

- 沿用同一运行的调用/Token 预算，用户确认不充值、不重置调用数。所有规划、成员、追问、继续和汇总调用都计费或占用预留。
- 新增 `active_ms/active_started_at`，仅动态模式用累计活跃时间计算时长；等用户时间不计入，重启恢复也不重置已消耗活跃时间。不是精确 CPU 时间，进程失联到重新领取之间仍可能保守计入活跃时间。
- `attempts` 保留累计领取次数；动态模式用 `recovery_attempts` 限制每个交互段最多三次领取，仅接受一条新的有效用户答复时重置段计数。正常多次人工交互不会耗尽三次恢复额度。
- 硬上限：六次负责人规划、二十四次成员任务（含同伴与继续）、四次同伴请求、八次用户交互（含派工确认），以及快照中的总调用数、Token 和活跃时长。规划耗尽直接失败，不静默跳过确认。
- 每个成员仍只可使用其快照中绑定的 Skill 和已加载包内文本，协议动作不授予 Shell、网络检索、桌面、MCP 或平台发布权限。
- 未知调用仍进入 `needs_review`，保留可能已花费的预留；人工答复不能绕过未知账本恢复或自动重发。取消等待任务直接关闭，已消费费用不退还。
- 上下文有界但不自动裁剪：大量成员长输出可能先触发输入上限而停止。不存在无限聊天、语义压缩、任意未来 DAG 或自动按供应商查询结果恢复。

## 5. 升级和验收边界

迁移 `1793836800000-dynamic-teams.ts` 只新增动作表、索引、运行计时/恢复列与等待状态约束。不改旧快照、正文或调用结果，拒绝破坏性 down。升级前停止写入、核对未知/在途任务、备份数据库及主密钥；CLI 显式迁移，再更新 API/Worker/Web。备份文件存在不等于恢复演练已通过。

测试使用专用 PostgreSQL 测试库、Redis DB 15 和本机 HTTP 模型 fixture，验证协议和恢复，不发生收费调用。浏览器 fixture 只能证明交互 UI；默认 mock 的本地预览不能演示真实动态团队成稿。真实模型配置后，先用小主题和保守预算人工试验，再评估质量与成本。

仍未实现：完整单专家多轮会话、用户人工编辑保存、内容审核动作、平台 HTML 导出、成员异构模型、任务级故障重试、版本恢复、专家制作向导、计划调度、视频生成、平台授权和自动发布。完整目标与缺口继续保留在 13，不因本轮动态协议完成而删减。
