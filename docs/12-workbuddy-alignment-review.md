# 12 WorkBuddy 专家与 Skills 对齐核对

> 核对日期：2026-11-02。
> 对照对象：本机安装的 WorkBuddy 5.3.5 与本次扩展前的 Creator-AI 源码。
> 状态：历史静态核对，保留当时结论；不是当前功能完成记录。
> 后续变更：用户已确认 D-011 的完整专家/Skills/专家团目标。本文推迟专家团的建议已被替代；最新代码状态与必做验收见 [实施状态](./10-implementation-status.md) 和 [能力对齐计划](./13-workbuddy-capability-plan.md)。文中“目前/当前”均指核对时点。

## 1. 结论

**目前没有真正对齐 WorkBuddy 的专家与 Skills。** Creator-AI 已具备独立专家、保存指令、选择技能、版本和任务快照的基础，但当前仍是配置与模拟执行原型，不是可扩展的专家运行系统。

最需要纠正的不是页面名称，而是三个概念：

1. 专家是可复用的角色定义和工作方式，不只是账号人设，也不只是技能组合。
2. Skill 是可加载的能力包，不等于固定枚举中的一段提示词，更不等于已经完成一次工具执行。
3. 保存配置、加载指令、调用模型、执行工具和产出通过验收，是不同阶段，不能混为一谈。

Docker Web 形态和当前技术栈可以保留。核对时建议先补齐单专家与技能的真实创作闭环，暂缓专家团等扩展；用户随后明确要求完整对齐，现按 D-011 将真实专家团列为必做，仍按单专家运行时到团队调度的依赖顺序交付。

## 3. WorkBuddy 中的专家

### 3.1 专家是一个可分发的角色包

随附专家规范包含：

- 清单：`.codebuddy-plugin/plugin.json`，记录标识、版本、展示信息、Agent 文件及可选 Skill 目录。
- 角色：`agents/*.md`，描述身份、能力、工作流程、输出要求和边界。
- 展示入口：职业、名称、简介、头像、标签、推荐问法等。
- 可选资源：Skills、参考资料、模板或配套工具。
- 类型：单个专家 `agent`，或者多角色专家团 `team`。

专家管理器还描述了两种创建方式：交互收集需求，以及把已有文档、流程和提示词转化为专家包。这是该随附 Skill 的设计流程，本轮没有实际创建专家验证。

### 3.2 Skill 并非专家的必填条件

`plugin-json-spec.md` 明确允许省略 `skills`。Agent Markdown 中的 `skills` 也是可选字段，其含义是“启动时预加载的 Skill”。

需要区分：

- 包里附带哪些技能资源。
- 专家启动时预加载哪些技能。
- 运行中根据任务按需加载哪些可用技能。

Creator-AI 目前只有一个 `skillKeys` 数组，尚未区分这些语义。

### 3.3 专家本身也可以有身份与口吻

此前“人设决定怎么说、专家负责怎么做”的说法是 Creator-AI 的产品分层建议，不是 WorkBuddy 的严格定义。其 Agent 规范本身包含角色身份，专家提示模板也有角色覆盖说明。

Creator-AI 仍应保留独立账号档案，因为同一个主笔需要服务不同公众号；但应明确：**专家可以有默认身份和表达习惯，生成某账号的内容时，以本次授权的账号表达要求为准。** 这属于本项目需要单独制定和测试的合并规则，不能声称照搬了 WorkBuddy。

### 3.4 专家团不能靠提示词假扮

随附团队规范描述了主理人、成员、分阶段 SOP、建立团队、调度和回传，明确反对主理人模拟所有成员输出。该规范不是本轮运行结果。

核对时的第一阶段方案仅支持单专家。按后续 D-011，专家团不再是可选事项，需要实际的成员执行记录、输入输出、预算、取消和失败恢复，不能把一次模型输出的多角色段落称为多 Agent 协作。

## 4. WorkBuddy 中的 Skills

### 4.1 文件形式

随附 Skill 创建规范描述了如下组织形式，附加目录都是可选的：

```text
skill-name/
  SKILL.md       YAML 元数据 + Markdown 指令
  references/    按需读取的说明与领域资料
  assets/        模板或产出所需资源
  scripts/       可选脚本，需要执行环境和工具支持
```

`name` 和 `description` 是基础元数据；描述同时帮助判断什么时候使用技能。部分示例带有额外的产品字段，不应将这些字段直接认定为跨产品通用协议。

Skill 可以只有文字指令，**并不是每个 Skill 都必须包含代码**。但只支持短文本常量，也不能声称支持完整技能包。

### 4.2 加载与使用

随附规范采用分层加载：先提供名称和描述，触发后加载正文，参考资料按需读取。专家提示模板要求通过 `Skill` 工具加载技能指令。

因此，“绑定技能”不意味着每次将所有技能正文和资料无差别拼接进提示词，也不意味着每个技能都是独立的一次模型调用。技能加载可以在同一个 Agent 执行过程中发生，实际文件读取或外部操作再由相应工具完成。

技能管理打包代码包含导入、创建、查找、启停、更新和市场安装入口；导入错误处理覆盖目录或 ZIP 缺失 `SKILL.md`、缺少名称或描述等情况。其入口和处理逻辑可从代码确认，但本轮未实际导入验证。

### 4.3 权限不能从文档内容直接授予

专家规范明确不允许在 Agent frontmatter 中声明 `tools`，工具由系统分配。Skill 文档中可能出现工具声明、命令和安装建议，但文档本身不能证明运行时授权已经完成。

Creator-AI 的服务端权限校验仍应保留。为了兼容文件格式而允许技能任意读取服务器或调用发布接口，是错误的对齐方式。

## 6. 当时的建议调整顺序

以下保留原核对时的建议：当时尚未修改业务实现或完成兼容性承诺。现在的必做顺序由 13 号计划 C1-C4 取代，不再以“评估是否做专家团”作为前提。

1. **先修订定义和验收。** 专家可绑定零到多项技能；取消三个固定技能的领域限制，保留合理数量和上下文预算限制；明确可用、预加载、已加载、已使用不是同一状态。
2. **建立独立技能库。** 支持创建、编辑、停用、版本化以及受限的 `SKILL.md` 导入；提供文件、依赖和兼容性预览。首批支持文字指令与安全的参考资料读取，不执行上传脚本。
3. **补齐单专家配置。** 保留简单表单，同时支持角色指令、推荐问法、技能选择和试用；账号可设置默认专家，日常只需输入选题或素材。
4. **接入真实执行。** 使用真实模型与受控技能加载工具；持久化专家/技能版本、实际加载和工具调用记录；支持同一篇内容继续修改。模型费用、超时和结果未知状态必须独立设计，不能直接套用 mock 的重复执行策略。
5. **再扩展包和协作。** 评估完整专家包导入导出、脚本沙箱、专家团与市场。任何 WorkBuddy 专用工具、依赖或平台接口都需明确适配，不能静默忽略后仍标记“完全兼容”。

建议的日常使用流程：

```text
一次性：建立账号档案 -> 配置默认专家 -> 安装/选择技能和参考资料
日常：选择账号 -> 输入主题或素材 -> 自动带入账号与专家上下文
执行：按需加载技能 -> 生成内容 -> 围绕同一内容继续修改
交付：编辑审核 -> 导出；发布作为单独授权步骤
```

### Docker 形态下需要坚持的差异

- 不承诺访问用户浏览器所在电脑的桌面应用或任意本地文件；需要上传、授权连接器或后续本地桥接方案。
- 导入仅表示解析并保存；安装、启用和具备执行能力应分别展示。包含未支持脚本或工具依赖时明确报告，不伪装成功。
- 校验压缩包路径、符号链接、文件数量和体积，防止路径穿越、解压炸弹和越权资源读取。
- 文本技能和参考资料也可能含提示注入；不得据此扩大账号权限、泄露密钥或触发自动发布。
- 若以后运行脚本，使用专门的受限执行环境和资源/网络策略，不把 Docker 本身视为完整安全保证；不给脚本应用密钥、宿主目录或 Docker Socket。
- 不直接复制 WorkBuddy 专家、技能正文或资源进入开源产品；分发前需核对各自许可证和授权。

## 7. 下一阶段应满足的验收

1. 不绑定 Skill 也能创建并使用单专家。
2. 新增一个未在代码枚举中的 Skill 后，无须改源码即可选择和使用。
3. 受支持的文字型 `SKILL.md` 可预览导入；缺失资源或不支持的工具依赖有明确提示。
4. 运行记录区分候选技能与实际加载的技能，能定位对应版本；不把“指令已加载”等同于“事实已查证”。
5. 同一专家服务两个账号时遵循各自表达和素材权限；修改专家或技能不改变历史任务快照。
6. 默认专家带入后，用户不必每次重复人设；同一篇内容可以继续修改，并经过审核导出。
7. 恶意 Skill 不能读取密钥、跨账号读取资料或绕过发布确认；禁止的脚本没有被实际执行。
